# dazpy Script-Call Batching and Main-Thread Backlog — Implementation Plan

> **Audience:** Claude Code implementation session. Validate each task and its
> acceptance criteria before proceeding. This plan intentionally separates
> safe SDK batching from optional server scheduling changes.

## Goal

Reduce the number of independent DazScript evaluations generated by dazpy,
especially for repeated transforms, property writes, pose operations, and
high-level convenience helpers. Preserve existing synchronous semantics while
making explicit batching easy and making backlog behavior measurable.

## Current behavior and constraints

- DAZ Studio DazScript execution must occur on Studio's main thread.
- Synchronous `/execute` requests cross from HTTP worker threads through
  `Qt::BlockingQueuedConnection`.
- `processNextAsyncRequest()` executes one queued async script at a time.
- `dazpy.Batch` already combines raw DazScript fragments into one HTTP request,
  but high-level proxy methods do not participate in it.
- A batch must be one DazScript evaluation. An endpoint that loops over many
  independent evaluations would reduce HTTP overhead but not main-thread
  scheduling overhead.
- Do not introduce implicit batching for ordinary property reads/writes. A
  normal getter must continue returning its value immediately.
- Do not change the existing Studio-busy fast-fail design in
  `docs/superpowers/specs/2026-07-22-studio-busy-handling-design.md`; this plan
  builds on it.

## Scope

### In scope

1. Fix helpers that accidentally issue multiple calls.
2. Add explicit high-level bulk operations.
3. Upgrade `Batch` so it can compose generated operations safely.
4. Add async batch submission as one queue item.
5. Add metrics for synchronous main-thread wait time and batch sizes.
6. Add unit, integration, and manual Studio validation.

### Out of scope

- Automatically delaying or reordering arbitrary user operations.
- Parallel DazScript execution inside Studio.
- Replacing all existing proxy APIs with a new transaction system.
- Making a batch partially commit or roll back. DazScript has no general
  transaction/rollback guarantee for scene mutations.

## Design decisions to validate before coding

Claude Code should stop after investigation and report any contradiction in
these decisions before implementing:

1. **One evaluation is the unit of batching.** `Batch` must generate one
   wrapper IIFE and one `/execute` request.
2. **Operations are ordered.** Reads can observe writes earlier in the same
   batch; the builder must not reorder operations unless an explicit future
   optimization adds dependency analysis.
3. **Results are keyed.** Each operation that returns a value receives a
   `BatchFuture`; mutation-only operations resolve to `None` or a documented
   success value.
4. **Errors fail the batch as a whole.** No fake partial-success contract is
   introduced in this change.
5. **Batch size is bounded.** Add configurable limits for operation count and
   generated script length before sending. Prefer a clear client-side error to
   creating an enormous Studio main-thread task.
6. **No implicit global queue.** The first implementation should not silently
   serialize every `DazClient.execute()` call. Explicit batching plus metrics
   gives callers control without changing latency semantics.

## Task 2 — Fix obvious multi-call helpers

### 2A. `DazElement.snapshot()`

Replace the loop over `get_property()` with one generated script that:

1. Resolves the owner once.
2. Iterates the requested labels inside Studio.
3. Returns a keyed object.
4. Uses `null` for missing properties, preserving current lookup semantics.

Tests:

- exactly one `client.execute()` call for multiple fields;
- all labels appear safely JSON-escaped in the generated script;
- missing owner/property behavior remains compatible.

### 2B. `reset_transforms()`

Generate one node script that sets position, rotation, and scale in order.
Do not call three proxy setters from the helper.

Tests:

- exactly one execute call;
- all three control families appear;
- existing values and public return behavior remain unchanged.

### 2C. `zero_figure()`

For the default mode, generate one Studio-side script that iterates bones and
non-zero morph channels and writes zero values directly. Avoid the current
read-all-then-write sequence.

For `include_props=True`, preserve the existing `DazPose.apply_full()` path
until a separate property semantics review confirms that direct zeroing is
safe with ERC links.

Tests:

- default mode uses one execute call;
- the script preserves the documented root-transform behavior;
- `include_props=True` behavior is unchanged.

## Task 3 — Add high-level bulk mutation APIs

### 3A. Node transforms

Add a method such as:

```python
node.set_transform(
    position=(x, y, z),
    rotation=(rx, ry, rz),
    scale=(sx, sy, sz),
)
```

Requirements:

- every argument is optional;
- omitted components are untouched;
- node lookup occurs once;
- values are serialized with the existing safe JSON helpers;
- missing nodes remain a no-op or raise exactly as the chosen existing setter
  contract documents.

### 3B. Element properties

Add a method such as:

```python
element.set_properties({"Smile": 0.8, "Blink": 0.2})
```

Requirements:

- one owner lookup;
- one property lookup per label inside Studio;
- documented missing-property behavior;
- no Python loop that calls `set_property()` repeatedly.

### 3C. Skeleton state

Review existing `set_bone_rotations()` and `set_morph_values()` before adding
duplicates. If both are needed together, add a combined operation such as:

```python
skeleton.set_state(bones=..., morphs=..., props=...)
```

It should use one script and preserve raw-vs-computed value rules already
documented in `_pose.py`.

Tests for each API must assert one execute call for multiple mutations and
must validate script safety with names containing quotes, backslashes, and
newlines.

## Task 4 — Upgrade `Batch` into a composable operation builder

Keep the existing raw-fragment API working. Extend it rather than replacing
it.

Suggested internal interface:

```python
batch.add_operation(
    body_lines=[...],
    result_expression="...",
)
```

Then add private/public helpers that high-level objects can use when a batch
is explicitly active.

Implementation requirements:

- unique variable namespace per batch;
- shared prelude support for node/skeleton lookups;
- result expressions are generated by the builder, not interpolated from
  arbitrary future keys;
- operation order is retained;
- empty batches perform no request;
- operation-count and script-length limits are checked before execute;
- context-manager exceptions do not submit the batch;
- failed execution leaves futures unresolved or marks them consistently with a
  documented terminal state—choose one and test it.

Do not make every existing proxy method batch-aware in this task. First expose
the primitive and migrate the helpers from Tasks 2–3. A later task can add a
context-local `client.batch()` dispatch mechanism once the operation protocol
is stable.

Tests:

- existing raw `Batch.add()` tests remain green;
- generated batch has one HTTP execute call;
- shared lookup is emitted once;
- read-after-write order is preserved;
- result values map to the correct futures;
- size limits fail before HTTP submission.

## Task 5 — Add one-request async batch submission

### Python API

Add a method such as:

```python
request_id = client.execute_batch_async(operations, args=None)
```

The method must submit one script to `/execute/async`, not one request per
operation. Provide the equivalent API in `_client_aio.py` if the async client
is considered public parity.

### Server API

Prefer reusing the existing async request shape by accepting one generated
script plus arguments. Only add a new `/execute/batch/async` route if the
existing payload cannot express the required operation metadata.

If a new route is added:

- it creates exactly one `AsyncRequestManager::AsyncRequest`;
- it consumes exactly one queue slot;
- it returns the normal request ID/status/result shape;
- it uses the same validation, authentication, body-size, and max-script
  length checks as `/execute/async`;
- cancellation semantics remain those of one script task.

Tests:

- a batch submission creates one tracked request;
- queue depth increases by one, not by operation count;
- result payload contains keyed operation results;
- queue-full behavior remains correct;
- cancellation and failure are documented as whole-batch behavior.

## Task 6 — Instrument synchronous backlog and batch execution

The current synchronous path hides queue wait inside Qt’s main-thread event
queue. Add metrics sufficient to distinguish queueing from execution:

- request accepted timestamp;
- main-thread dispatch timestamp;
- execution start timestamp;
- execution completion timestamp;
- `main_thread_wait_ms`;
- `execution_duration_ms`;
- batch operation count;
- generated script byte length.

For synchronous requests, maintain a bounded atomic counter or equivalent
diagnostic counter around the `BlockingQueuedConnection` handoff. Do not add a
second unbounded queue.

For async requests, expose existing queue depth plus the new batch metadata.
Update `/metrics` and logs without breaking existing JSON fields.

Tests:

- metrics remain valid when fields are zero or unavailable;
- concurrent requests do not corrupt counters;
- batch metadata is present only when applicable;
- existing metrics consumers remain compatible.

Manual Studio smoke test:

1. Start the server with metrics enabled.
2. Run 100 individual property/transform operations and record request count,
   total wall time, Studio responsiveness, and main-thread wait metrics.
3. Run the equivalent operation as one synchronous batch.
4. Run it as one async batch and inspect `/requests/:id/status`.
5. While a scene load or render is active, verify the existing `503
   STUDIO_BUSY` behavior remains fast and does not enqueue duplicate work.
6. Verify a deliberately failing operation reports whole-batch failure and
   does not falsely claim rollback.

## Acceptance criteria

- Repeated bulk operations use one DazScript evaluation per logical group.
- `snapshot()`, `reset_transforms()`, and default `zero_figure()` no longer
  issue one HTTP request per field/component.
- Existing public APIs and raw `Batch` usage remain compatible.
- High-level batching has deterministic ordering and keyed results.
- Async batch consumes one queue item.
- Synchronous wait time is observable separately from script duration.
- No new automatic retry or implicit global serialization is introduced.
- Unit tests prove call-count reductions; manual Studio testing confirms lower
  backlog and preserved scene behavior.
